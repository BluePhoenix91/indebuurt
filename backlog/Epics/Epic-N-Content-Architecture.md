# Epic N — Content Architecture & Build Pipeline

**Goal:** Separate AI-generated prose from data-driven content, enabling $0 refreshes when POI/statistics data changes.

**Depends on:** Epic M (API Infrastructure), Epic L (Agent Fine-Tuning)

**New project:** `pipeline/` (.NET 10, ASP.NET Core) — *created in Epic M*

---

## Context

Currently, the entire neighborhood JSON is generated by AI agents. When OSM data updates (new vet, new park), we must regenerate the full content at ~$0.22/neighborhood. For 2,800 neighborhoods, a single data refresh costs ~$450.

This epic separates:

- **Prose** (intro, subtitle) → AI-generated once, stored in database
- **Structured content** (value cards, labels) → Templates filled from live data
- **POI lists** (vets, parks, etc.) → Queried from GIS at build time

After implementation, data refreshes cost $0. AI is only needed for prose rewrites.

## Story N1: Content Database Schema

> As a developer, I want a separate content database schema, so that AI-generated prose is stored independently from GIS data.

**Acceptance Criteria:**

- [x] Schema created in `pipeline/` project as EF Core migrations
- [x] Can run on same PostgreSQL instance as GIS (separate schema)
- [ ] Seed data for `value_card_templates` (6 card types) — *deferred to N3*
- [ ] Seed data for `label_rules` (initial set of ~10 rules) — *deferred to N4*
- [ ] Foreign key to GIS `neighborhoods` table for validation — *deferred to Epic O (when GIS entities added to DbContext)*

**Implementation Notes (completed 2026-01-24):**

*Schema changes from original plan:*

| Original | Implemented | Reason |
|----------|-------------|--------|
| `nis_code VARCHAR(14)` | `VARCHAR(7)` | Matches actual NIS code length in GIS data |
| `poi_category` column | Removed | Derived from `CardType` via `PoiCategoryMapper` |
| `icon`, `distance_icon` columns | Removed | Derived from `CardType` via `IconMapper` |
| `priority`, `max_labels` columns | Removed | Replaced with `Category` enum; ordering handled by frontend |
| `condition_field VARCHAR` | `ConditionField` enum | Type safety |
| `condition_op VARCHAR` | `ConditionOperator` enum | Type safety |
| `SERIAL` primary key | `GUID v7` | Consistency across all entities |

*Final schema:*

```sql
-- content.neighborhood_prose
nis_code        VARCHAR(7) PRIMARY KEY
slug            VARCHAR(200) NOT NULL UNIQUE
city            VARCHAR(200) NOT NULL
name            VARCHAR(200) NOT NULL
intro           TEXT NOT NULL
subtitle        VARCHAR(400) NOT NULL
quality_score   DECIMAL(4,1)
prompt_version  VARCHAR(20)
generated_at    TIMESTAMP NOT NULL
modified_at     TIMESTAMP
modified_by     VARCHAR(100)

-- content.value_card_templates (~6 rows)
card_type               VARCHAR(50) PRIMARY KEY  -- Enum: DogParks, Parks, Vets, etc.
title                   VARCHAR(100) NOT NULL
description_template    VARCHAR(200) NOT NULL
detail_template         VARCHAR(200) NOT NULL
sort_order              INTEGER NOT NULL

-- content.label_rules
id                  UUID PRIMARY KEY  -- Guid v7, app-generated
category            VARCHAR(50) NOT NULL  -- Enum: Character, Amenities, Transport, Demographics
label_text          VARCHAR(100) NOT NULL
label_icon          VARCHAR(100) NOT NULL
condition_field     VARCHAR(50) NOT NULL  -- Enum: ParkCount, DogParkCount, etc.
condition_operator  VARCHAR(20) NOT NULL  -- Enum: GreaterThan, LessThan, Between, etc.
condition_value     VARCHAR(50) NOT NULL
```

*Code structure:*
- Entities: `Pipeline.Core/Entities/Content/`
- Configurations: `Pipeline.Core/Data/Configurations/Content/`
- Enums: `Pipeline.Core/Enums/` (CardType, LabelCategory, ConditionField, ConditionOperator)
- Mappers: `Pipeline.Core/Mappers/` (IconMapper, PoiCategoryMapper)

*Key decisions:*
- Enums stored as strings (`.HasConversion<string>()`) for readability and safety against reordering
- Icons and POI categories derived from `CardType` via mappers (not stored in DB)
- `LabelCategory` enum for grouping labels; display order determined by frontend
- Single `PipelineDbContext` manages all schemas (gis, pipeline, content)
- Migration history in `gis.__EFMigrationsHistory`

*Migration:*
```bash
cd pipeline
dotnet ef migrations add CreateContentSchema --project src/Pipeline.Core --startup-project src/Pipeline.Api
dotnet ef database update --project src/Pipeline.Core --startup-project src/Pipeline.Api
```

## Story N3: Value Card Template System

> As a developer, I want value cards generated from templates and live data, so that counts update automatically without AI.

**Template Example:**

| card_type | description_template                    | detail_template                                   |
| --------- | --------------------------------------- | ------------------------------------------------- |
| dog_parks | {count} hondenspeelweiden binnen bereik | Dichtstbijzijnde omheind op {nearest_minutes} min |
| parks     | {count} parken in de buurt              | {nearest_name} op {nearest_minutes} min lopen     |
| vets      | {count} dierenartsen binnen 30 min      | {nearest_name} op {nearest_minutes} min           |

**Build Logic:**

```csharp
public ValueCard BuildValueCard(string nisCode, ValueCardTemplate template)
{
    var count = _gisDb.GetPoiCount(nisCode, template.PoiCategory);
    var nearest = _gisDb.GetNearestPoi(nisCode, template.PoiCategory);

    return new ValueCard
    {
        Icon = template.Icon,
        Title = template.Title,
        DistanceIcon = template.DistanceIcon,
        Description = template.DescriptionTemplate
            .Replace("{count}", count.ToString()),
        Detail = template.DetailTemplate
            .Replace("{nearest_name}", nearest.Name)
            .Replace("{nearest_minutes}", nearest.WalkingMinutes.ToString())
    };
}
```

**Acceptance Criteria:**

- [ ] `ValueCardTemplate` entity with EF Core mapping
- [ ] `ValueCardBuilder` service that fills templates from GIS data
- [ ] Handles edge cases: count=0, no nearest POI found
- [ ] Unit tests for template replacement logic
- [ ] Seed data for 6 card types (dog_parks, parks, vets, pet_stores, supermarkets, transit)

## Story N5: Content Build Script

> As a pipeline operator, I want a build command that assembles final JSON from prose + live data, so that I can refresh content without AI costs.

**Command:**

```bash
dotnet run -- build                     # Build all published neighborhoods
dotnet run -- build --nis 44021A0       # Build single neighborhood
dotnet run -- build --municipality 44021 # Build all in municipality
dotnet run -- build --changed           # Build only where GIS data changed
```

**Build Process:**

```
For each neighborhood in neighborhood_prose:
  1. Load prose (intro, subtitle) from Content DB
  2. Load counts from mv_neighborhood_poi_counts (GIS)
  3. Load nearest POIs from mv_neighborhood_nearest_pois (GIS)
  4. Load statistics from neighborhood_statistics (GIS)
  5. Apply label_rules → generate labels[]
  6. Apply value_card_templates → generate valueCards[]
  7. Assemble final JSON matching Astro schema
  8. Write to web/src/content/neighborhoods/{slug}.json
```

**Acceptance Criteria:**

- [ ] `BuildCommand` CLI command implemented
- [ ] Reads from both Content DB and GIS DB
- [ ] Assembles JSON matching existing Astro schema exactly
- [ ] Supports single, municipality, and full builds
- [ ] `--changed` flag detects GIS data updates (compare timestamps)
- [ ] Reports build statistics (count, duration, errors)
- [ ] Validates output against Zod schema before writing

## Story N7: Deprecate Brand Reviewer JSON as Source

> As a pipeline operator, I want the build script to be the only publisher, so that content always reflects latest data.

**Current Flow:**

```
Brand Reviewer → 4-brand-reviewer.json → copy to web/src/content/
```

**New Flow:**

```
Writer → neighborhood_prose (DB)
Build Script → web/src/content/{slug}.json
```

**Acceptance Criteria:**

- [ ] Remove auto-publish from pipeline command
- [ ] Build script is only way to generate published JSON
- [ ] `pipeline` command updates DB, does not write to `web/src/content/`
- [ ] Document new workflow in pipeline docs
- [ ] Add `--publish` flag to build command for explicit publishing

## Cost Impact

| Scenario                 | Before                           | After              |
| ------------------------ | -------------------------------- | ------------------ |
| OSM monthly refresh      | ~$450 (regenerate all)           | $0 (build script)  |
| New vet opens            | ~$0.22 (regenerate neighborhood) | $0 (build script)  |
| Statbel annual update    | ~$450                            | $0 (build script)  |
| Fix prose typo           | Manual JSON edit                 | DB update + build  |
| Rewrite intro completely | ~$0.05 (one neighborhood)        | ~$0.05 (unchanged) |

**Break-even:** After 1 OSM refresh cycle, the architecture pays for itself.
